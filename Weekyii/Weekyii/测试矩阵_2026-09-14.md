## 0. 执行方式

```bash
cd Weekyii
xcodebuild -scheme Weekyii \
  -destination 'platform=iOS Simulator,name=iPhone 17 Pro' \
  OTHER_SWIFT_FLAGS='$(inherited) -Xfrontend -disable-sandbox' \
  -only-testing:WeekyiiTests/WeekCalculatorTests \
  -only-testing:WeekyiiTests/NotificationServiceTests \
  -only-testing:WeekyiiTests/StateMachineTests \
  -only-testing:WeekyiiTests/ModelTests \
  -only-testing:WeekyiiTests/SuspendedTaskLifecycleServiceTests \

```

* 必须带 `-Xfrontend -disable-sandbox`，否则本机 `sandbox-exec: sandbox_apply: Operation not permitted`
  会让 SwiftData 宏展开假性失败（见 `编译排错记录.md` #22）。
* `TaskPostponeServiceTests` **排除在外**：iOS 26 模拟器 + SwiftData 类型转换崩溃导致 runner 重启循环，
  属改动前既有问题，不是本轮回归。

## 1. P0：悬置箱到期策略（`SuspendedExpiryPolicy`）

风险：策略默认行为若变化，老用户升级后会发现「悬置箱不再自动清理」；策略若读不到，可能永远不删也可能误删。

| # | 用例 | 位置 | 验证点 |
| --- | --- | --- | --- |
| 1.1 | `test_userSettings_suspendedExpiryPolicyDefaultsToAutoDeleteAndPersists` | ModelTests | 默认 `.autoDelete`、写入即持久化、重读生效 |
| 1.2 | 同上（后半段） | ModelTests | 脏值 `"something-else"` → 回落 `.autoDelete` |
| 1.3 | `test_sweepExpiredSuspendedTasksDeletesExpiredRecordsAndCancelsNotifications` | ModelTests | `.autoDelete` 删除过期项、取消其通知、保留未过期项 |
| 1.4 | `test_sweepExpiredSuspendedTasksKeepsOverdueRecordsUnderKeepOverduePolicy` | ModelTests | `.keepOverdue` 下删除数 0、通知不取消、状态仍 `.active`、重复执行幂等 |
| 1.5 | `test_reconcile_deletesExpiredSuspendedTasksWhenPolicyIsAbsent` | StateMachineTests | **端到端**：未写入过 key 的首装场景，`reconcile` 仍删除（`suspendedAutoDeletedCount == 1`） |
| 1.6 | `test_reconcile_keepsOverdueSuspendedTasksUnderKeepOverduePolicy` | StateMachineTests | **端到端**：`UserDefaults.standard = keepOverdue` 时记录存活，二次 reconcile 仍存活 |
| 1.7 | `test_reconcile_fallsBackToAutoDeleteWhenPolicyValueIsUnreadable` | StateMachineTests | **端到端**：脏值回落 `.autoDelete` |
| 1.8 | `test_suspendedPlan_dueDayEveningBodyReflectsExpiryPolicy` | NotificationServiceTests | 推送文案随策略切换（不再在 keepOverdue 下谎称「将自动删除」） |

补充设计说明：
* 1.5~1.7 走的是真实生产路径 `StateMachine.reconcile → Self.suspendedExpiryPolicy → sweepExpiredTasks`，
  此前只有 service 层与 `UserSettings` 层被覆盖，这条链是本次补齐的缺口。
* 三个用例通过 `withExpiryPolicy(_:)` 包装器写 `UserDefaults.standard` 并在 `defer` 中原值还原，
  避免 `keepOverdue` 泄漏污染同进程其它用例。

## 2. P1~P3：新增设置项

风险：`UserSettings` 是 `ObservableObject` + `didSet { save() }`，漏掉一次 `save()` 会「编译通过、重启丢失」；
同时 `save()` 会把节奏配置推给全局单例 `NotificationService.shared.configuration`，容易跨测试污染。

| # | 用例 | 位置 | 验证点 |
| --- | --- | --- | --- |
| 2.1 | 保留份数 / 恢复点份数持久化用例 | ModelTests（`backupRetentionCount`、`recoveryPointRetentionCount`） | 默认值 + 写入后重读 |
| 2.2 | `test_userSettings_*`（节奏类） | ModelTests | 早晨/晚间/悬置提醒时间点与开关 |
| 2.3 | `ModelTests.tearDown()` | ModelTests | 每个用例后把 `NotificationService.shared.configuration` 复位为 `.default` |
| 2.4 | 「可配置节奏」7 条 | NotificationServiceTests | 通知计划随新设置项变化 |

> 2.3 是为修复**真实污染**而加的：`ModelTests` 在 `NotificationServiceTests` 之前按字母序执行，
> 前者把单例改成 6:30 / 关闭悬置提醒后，后者未显式传 `configuration:` 的旧用例会失败。

### 关于「条」：一次真实的修复

`ThemeVisualStyle` 原本声明了 `barStrokeWidth`，但**没有任何视图消费它**——是个死旋钮。
本次改为 `barScale`（倍数）+ `barCornerRadius`（nil = pill），并在 `ProgressRing.swift` 的三个组件
（`ProgressRing` / `MiniProgressRing` / `ProgressBar`）中真正接线。

之所以用倍数而不是绝对宽度：调用点传的是 4、8、12 三种基准值，
只有「经典 = 1.0」才能保证 10 套原主题的条形粗细一像素不变。
`ProgressBar` 的容器高度也必须跟着 `themedHeight` 走，否则放粗到 1.5 倍的条形会被自己的容器裁掉。

一处更正：上一条曾说「`ProgressRing.swift` 是条的唯一汇聚点」。复核后发现 `KillTimeSlider`
自带一条 4pt 轨道（未走 `ProgressRing`），本轮已一并接线。
Features 目录下的其它 `Capsule` 经核对均为徽章/分段指示器，不是进度条，故不处理。

### 主题选择器：让形态可见

设置页的 `ThemePaletteMark` 原本是硬编码的 30×30 双色块（圆角 7、描边 0.5pt），
**14 套主题除了色相之外长得一模一样**，新主题的形态差异在选择器里完全看不出来。
现改为从 `visualStyle` 派生（`swatchRadius` / `swatchBorderWidth`），
缩放系数刻意取成让经典主题精确还原 7pt / 0.5pt，并由 4.9 号用例钉住。
色块描边同样区分明暗，否则墨黑描边在深色行上会消失。

> 色块刻意**不渲染阴影**：经典主题原本没有阴影，加上就破坏了「原主题零变化」。
> 代价是粗野主题的硬阴影在色块上看不出来，只在真实卡片上体现。

### 视觉验证（截图实测）

通过 `WeekyiiUITests` 新增的 `ThemePickerScreenshotTests` 自动接受通知弹窗、
进入设置→外观与主题并滚动到底，截图（`/tmp/weekyii_shots/uitest_picker*.png`）。
确认 4 套个性化主题色块的形态差异肉眼可辨：
* **粗野** = 近乎直角 + 粗黑描边
* **霓虹** = 较大圆角 + 青色描边
* **纸感** = 近乎直角 + 最细描边
* **终端** = **完全直角** + 磷光绿描边

经典主题（薄荷/极夜/魔戒）形态完全一致，与设计意图一致。
另逐套切到 `brutal/neon/paper/terminal/amber` 后截了「今日」页（`/tmp/weekyii_shots/*.png`），
通知弹窗会挡住卡片主体但顶部颜色和插图证明主题生效。

**深色模式**（`xcrun simctl ui booted appearance dark` + 同上截图流程 → `dark_*.png`）：
* 4 套个性化主题全部通过——明暗双描边色起作用（粗野墨黑→`#F2F2F2` 浅灰、
  终端深绿→`#33FF66` 磷光绿、纸感 `#D6C9B4`→`#4A453D`、霓虹 `#0091A8`→`#00F0FF`）。
* 纸感朱红字标在深底上像红墨，效果有意。
* 粗野深色下硬阴影（`#000000` 不透明）几乎被 `#111111` 深底吞掉，
  浅灰边框兜住了卡片边界——视觉可接受，未改。

待手工确认（无自动化，按设备逐个切换 14 套主题）：
* 切到「粗野」：卡片圆角变 4、2.5pt 墨黑描边、4×4 硬阴影（无模糊）、SF Symbol 变 fill、进度条明显加粗且方角。
* 切到「霓虹」：卡片圆角 14、1.5pt 描边、青色发光阴影、图标 fill、进度条略粗。
* 切到「纸感」：卡片近乎直角（圆角 2）、0.75pt 发丝描边、**完全无阴影**、进度条变细、图标保持描边。
* 切到「终端」：卡片**完全直角**（圆角 0）、1pt 磷光绿描边、无阴影、图标 fill、进度条方角。
* 切回任意原主题：视觉与改动前完全一致（这是 4.1/4.5/4.6 要守护的东西）。
* 深色模式下「粗野」的墨黑边框应自动翻转为浅色 `#F2F2F2`，否则描边在深底上消失。
* 深色模式下「纸感」的描边为 `#4A453D`，「终端」为亮绿 `#33FF66`（与浅色不同值，见 4.2）。
