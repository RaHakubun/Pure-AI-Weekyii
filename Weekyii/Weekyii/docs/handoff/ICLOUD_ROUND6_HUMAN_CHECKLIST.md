## 1. 真机场景（按顺序做，后面的依赖前面的状态）

### 1.1 首次开启 · 云端为空

- [ ] 设置 → iCloud 同步 → 打开开关。
- **预期**：出现“云端没有数据”类提示，只有一个“上传本机”方向的选择；选择后状态变“已同步”，本机数据条数不变。
- **失败时记**：开关打开后是否有任何弹窗、状态文案、以及 Console 里 `Weekyii` 关键字的前 20 行日志。

### 1.2 首次开启 · 云端非空

- [ ] 在设备 A 已有数据的前提下，用设备 B（本机有不同数据）打开同步开关。
- **预期**：出现“以哪份数据为准”，三个选项：用本机 / 用云端 / 合并。
- [ ] 选“合并”。**预期**：两端条数相加（去重后），没有条目丢失。
- [ ] 换第三台设备重复一次，选“用云端”。**预期**：本机数据被云端替换，云端不受影响。
- [ ] 再换一台，选“用本机”。**预期**：先弹二次确认并写明“将删除 N 项”，确认后云端被本机数据替换。

### 1.3 首次开启 · 云端有本版本读不懂的记录（关键，对应本轮修复）

- [ ] 设备 A 正常同步一条任务，记下它的 `recordName`（Console → Records 里能看到）。
- [ ] 在 CloudKit Console → Production → Records → `WeekyiiSyncZoneV1` 打开该记录，把 `payloadVersion` 从 `1` 改成 `2`，保存。
- [ ] 设备 B（本机有数据、尚未开启同步）打开同步开关。
- **预期**：
  - 出现“需要先更新 Weekyii”，**没有任何**数据来源按钮（只有取消/关闭）。
  - 设置页状态行显示“需要更新 Weekyii 后才能继续”。
  - Console 里那条 `payloadVersion = 2` 的记录**仍在**，没有被删除。
  - 设备 B 的本机数据**没有**被合并、也没有被清空。
- [ ] 把 `payloadVersion` 改回 `1`，重新开启同步。**预期**：恢复正常，能正常选择。
- **失败时记**：截图弹窗 + Console 里该记录是否还在 + 设备 B 的数据条数变化。
- **注意**：这是唯一能真正验证“隔离 + 拒绝破坏性操作”的场景，务必做。

### 1.4 换账号

- [ ] 设置 → Apple ID 退出，换另一个 Apple ID 登录，回到 Weekyii。
- **预期**：出现“账号已变更”，三个选项。分别测：
  - [ ] 用新账号云端数据 → 本机被替换，新账号云端不变。
  - [ ] 用本机数据 → 二次确认后新账号云端被本机替换。
  - [ ] 合并 → 两边相加。
- [ ] 重复 1.3 的 `payloadVersion = 2` 造数步骤，再触发换账号。
- **预期**：换账号弹窗直接显示“另一个 iCloud 账户中有由更新版本 Weekyii 写入的数据，本次未做任何更改”，三个按钮**全部置灰**，只有取消可用。新账号云端那条记录仍在。
- **失败时记**：按钮是否可点、点击后发生了什么、目标账号云端条数变化。

### 1.5 云端 Zone 被删后不锁存

- [ ] 设置 → Apple ID → iCloud → 管理账户存储 → Weekyii → 删除数据。
- [ ] 回到 Weekyii，下拉或点“立即同步”。
- **预期**：不进入永久失败/“同步已暂停”，而是重新进入首次启用决策（云端为空 → 提示上传本机）。
- **失败时记**：状态文案 + 是否能通过“立即同步”恢复。

### 1.6 双设备并发编辑

- [ ] 两台都断网（飞行模式）。
- [ ] 两台各自修改**同一条**任务标题，改成不同内容。
- [ ] 两台都恢复网络，等同步完成。
- **预期**：两端最终一致；先联网那台的标题获胜。设置页出现“上次同步的冲突 1 处（已保留本机版本）”。
- **失败时记**：两端最终标题、冲突计数、以及是否有一端反复回退。

### 1.7 附件跨设备

- [ ] 设备 A 给任务加一张图片附件和一份文件附件。
- [ ] 设备 B 同步后打开该任务。
- **预期**：图片能显示，文件能打开，文件名正确。
- **失败时记**：附件是缺失、还是显示为占位、还是打不开。

### 1.8 离线编辑后补传

- [ ] 设备 A 断网，新建 3 条任务、删除 1 条。
- [ ] 恢复网络，等同步。
- **预期**：设备 B 看到 3 条新增、1 条被删；没有重复条目。
- **失败时记**：重复条目的标题与数量（这是 M2 类问题的真机信号）。

### 1.9 VIP 到期与续订

- [ ] 用沙盒账号让订阅过期（或退款模拟）。
- **预期**：状态变“同步已暂停：VIP 未开通或已到期”，本地数据完好，设置页出现“续订会员以恢复 iCloud 同步”。
- [ ] 点续订完成购买。
- **预期**：自动恢复同步，不需要关开关再打开。
- **失败时记**：续订后状态是否停在 `.locked`。

### 1.10 归档导入前自动关同步

- [ ] 同步开启状态下，设置 → 数据 → 导入归档。
- **预期**：导入前同步被自动关闭，导入完成后提示需要重新开启；重新开启时重新询问以哪份数据为准。
- **失败时记**：导入后另一端数据是否被“推平”（这是数据事故级问题，务必确认）。

## 5. 代码侧遗留：我评估后没做，交给你决定

### 5.1 快照仍把附件字节全量读进内存（原 H3 的残留）

现状：`CloudSyncReconciler` 每轮会读 3 次全库快照（`:95`、`:106`、`:167`），每次都会把 `TaskAttachment.data` 和 `MindStampItem.imageBlob` 的完整字节读进内存。原来「每个远端获胜记录读一次全库快照」的 O(n) 问题已经修掉了（第五轮），剩下的只是常数 3，但常数里带着附件字节。

为什么没做：正确做法是给附件加一个写入时算好的 `contentHash` 存储属性，快照只带哈希，字节只在真正上传/下载该实体时按需读。这需要 SwiftData 迁移（新增存储属性）+ 改所有附件写入路径 + 改 `WeekyiiSnapshotMergeService` 的相等语义 + 补迁移测试。**没有大库基准就改它，等于用「可能漏检变化」换「可能更快」**，而漏检变化会直接导致同步不应用数据。

建议顺序：先在真机上导一个 100 MB 附件库，量一下一轮同步的峰值内存和耗时；如果确实超预期，再按上面的方案做，并且必须有一条「改回缺陷必须失败」的对照测试。
